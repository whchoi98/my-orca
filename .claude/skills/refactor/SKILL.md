# 리팩터링

동작은 그대로 두고 구조만 수정합니다.

## 원칙
- 동작을 바꾸지 않습니다. 동작을 바꿔야 하면 리팩터링과 따로 다룹니다
- 작은 단계로 나누고 단계마다 시험을 실행합니다
- 요청받은 범위만 수정합니다. 범위 밖의 정리는 제안으로 남깁니다
- 추상화는 같은 코드가 실제로 반복될 때만 넣습니다

## 절차

### 1. 지금 상태 확인
- 수정할 코드와 그 코드를 부르는 곳을 읽습니다
- 시험이 그 코드를 다루는지 확인합니다. 다루지 않으면 먼저 지금 동작을 고정하는 시험을 넣습니다
- 스택 코드를 수정할 때는 수정 전 템플릿을 저장해 둡니다: `(cd infra-cdk && npx cdk synth <스택> -c stackName=<스택> > <수정 전 파일>)`
- Terraform 코드를 수정할 때는 수정 전의 계획을 저장해 둡니다: `bash deploy_orca_tf.sh --plan`의 출력. 계획은 읽기만 합니다

### 2. 시험이 통과하는지 확인
```bash
npm test --prefix infra-cdk
bash infra-tf/run-tests.sh
bash tests/run-all.sh
(cd infra-cdk && npx tsc --noEmit -p .)
```

### 3. 한 단계씩 수정
- 한 번에 한 가지만 바꿉니다(이름, 추출, 이동 가운데 하나)
- 바꿀 때마다 위 시험을 다시 실행합니다
- 스택 코드는 수정 뒤의 템플릿이 수정 전과 같은지 비교합니다. construct ID가 바뀌면 리소스가 교체됩니다
- Terraform 코드는 수정 뒤의 계획이 수정 전과 같은지 비교합니다. 리소스 주소(이름, `count`, `for_each`의 키)가 바뀌면 이미 배포한 리소스가 교체됩니다. 주소를 바꿔야 하면 `moved` 블록을 씁니다

### 4. 마무리
- `infra-cdk/lib/host/` 아래 스크립트를 수정했으면 `ScriptSha256`이 달라져 다음 배포에서 서버의 설치가 다시 실행된다는 점을 보고합니다
- `infra-cdk/lib/gate/`를 수정했으면 묶음 주소가 달라져 같은 일이 일어납니다
- 위 두 디렉터리는 Terraform 배포도 그대로 씁니다. Terraform으로 배포한 서버에서도 다음 apply에서 설치가 다시 실행됩니다

## 하지 않는 것
- 배포. 리팩터링한 코드를 배포하려면 `/deploy`의 승인 절차를 따릅니다
- 자산 디렉터리에 파일을 더하는 일(자산 해시가 바뀝니다)
